**运行时实例**是一个运行的生产运行时，为动态部署提供服务。静态部署没有运行时实例；它们由不可变的静态工件提供服务。

> **注：阶段状态**
>
> 面向调用者的合约是稳定的：动态部署启动生产运行时，等待运行状况检查，并且仅在新版本准备就绪时进行升级。您不需要知道 MIOSA 如何放置或协调这些运行时。

## 什么是运行时实例

运行时从客户发布开始。该版本是客户的应用程序，已完全打包。运行时间：

1. 几秒钟内即可启动。
2. 接收 `PORT`（发布端口，除非您自己设置）、`DATABASE_URL`、`AUTH_URL` 以及 MIOSA 在启动时注入的其他环境变量。
3. 启动配置的`run_command`。
4. 收听 `port`。
5. 用 2xx 响应 `GET health_check_path`。
6. 加入部署的后端池；路由器开始向其发送流量。

当运行时实例死亡（崩溃、主机故障、配置重启）时，MIOSA 的协调器会注意到并安排在另一台健康主机上进行替换。

## 它运行的地方

每个运行时实例都在 MIOSA 管理的主机上自己的 microVM 中运行。
不同客户的运行时在网络上相互分段，运行时只能访问您链接到它的服务以及公共互联网。
重新启动主机智能体不会停止正在运行的实例。
当它回来时，智能体会重新连接到它。

## 您的应用程序必须使用的端口

MIOSA 将 `PORT` 设置为版本的端口（默认情况下为服务 `port`、`8080` ），除非您自己在部署的环境变量中设置 `PORT`。
您的应用程序必须在所有接口 (`0.0.0.0`) 上侦听该端口，而不仅仅是 `127.0.0.1` 上。
MIOSA 从 microVM 内部访问它并将其发布到实例的地址。
API 报告的实例的地址和端口是 MIOSA 路由器到达它的位置，并不总是运行时的私有地址。

## Next.js 应用程序

在 `next.config` 中设置 `output: "standalone"`。
当构建生成 `.next/standalone/server.js` 时，MIOSA 会在其旁边复制 `public` 和 `.next/static` 并运行：

```bash
HOSTNAME=0.0.0.0 node .next/standalone/server.js
```

独立版本带有自己的跟踪 `node_modules`，因此 MIOSA 不会在运行时重新安装依赖项。
如果没有独立输出，Next.js 应用程序将以 `next start` 开头，并且需要完整的构建。

## 需要构建输出

Next.js 版本必须包含其生产版本： `.next/BUILD_ID` 必须存在于版本中。
只有源树的版本无法运行，因为 `next start` 会随着 `Could not find a production build` 立即停止。
MIOSA 在发布时拒绝此类发布，并在启动时再次拒绝此类发布，并出现错误 `build_output_missing`。
通过在创建发布之前运行构建或让 MIOSA 构建应用程序并再次发布来修复此问题。

## 当启动失败时

当发生以下任一情况时，运行时实例启动失败，并且该实例将被删除：

|错误 |意义|
|---|---|
| `release_install_failed` |下载、验证或解压该版本失败。错误包含退出代码和步骤的最后输出。 |
| `build_output_missing` | Next.js 版本没有生产版本（见上文）。 |
| `app_launch_failed` |无法启动启动命令。 |
| `app_not_listening` |该应用程序已启动，但未应答其端口上的运行状况检查。 |

对于 `release_install_failed`、`app_launch_failed` 和 `app_not_listening`，部署的错误消息包括应用程序日志的尾部、运行时中运行的进程以及它正在侦听的端口，因此您可以了解它没有出现的原因。
首先阅读：常见原因是应用程序绑定了 `127.0.0.1` 而不是 `0.0.0.0`、错误的 `port`、缺少依赖项或缺少构建。
由于失败的实例已被删除，因此失败的启动永远不会提供流量，并且先前的版本将保持活动状态。

## 您控制的内容与 MIOSA 控制的内容

| 你 | MIOSA |
|---|---|
|发布内容（您的代码+依赖项）|在哪里安排实例 |
| `run_command` 和 `port` |何时启动/停止/替换实例 |
| `health_check_path` |将健康实例路由至流量 |
|所需的副本数量（最终；默认为 1）|启动时环境变量注入 |
|部署中设置的环境变量 |遥测、日志流 |

您不直接选择主机。 MIOSA 的调度程序将您的工作负载需求（CPU、RAM、区域）与队列的可用容量相匹配。

## 生命周期

等待进入按计划开始；检查通过后开始进入健康状态；健康在于停止拆卸；停止去停止。

如果检查失败，启动就会变得不健康；不健康就停止更换。

开始因崩溃循环预算而失败。

- `pending`：已安排，尚未启动。
- `starting`：虚拟机正在启动；健康检查尚未通过。
- `healthy`：服务流量。
- `unhealthy`：健康检查失败；路由器已将其从池中删除。 Reconciler 决定是否重新启动或替换。
- `stopping` / `stopped`：故意拆掉。
- `failed`：终端，超出了崩溃循环预算。协调器停止尝试。

## 健康检查和宽限期

当运行时实例启动时，它有一个可配置的宽限期（默认 60 秒）才能变得健康。在宽限期间，可以容忍重复的 5xx/连接拒绝。

宽限期后，严格执行健康检查：

- 连续 3 次失败 → 标记为 `unhealthy` 的实例，已从路由中删除。
- 如果需要替换并正常启动，则旧实例将被拆除。
- 重复的快速故障会调用崩溃循环退避：重新启动尝试之间的间隔为 1 秒 → 2 秒 → 5 秒 → 30 秒 → 5 分钟。

## 发布期间的蓝色/绿色

当您发布新的动态版本时，MIOSA 不会首先终止现有的健康实例。顺序是：

1. 从新版本启动新的运行时实例。
2. 等待足够多的新实例通过健康检查。
3. 更新路由器，以便部署的主机名指向新实例。
4. 旧的正在进行的请求完成后，Drain（停止接受新连接）并拆除旧实例。

如果步骤 2 从未成功，则步骤 3 永远不会运行。旧版本仍然有效，新版本标记为 `failed`。

## 副本

默认情况下，动态服务有 1 个副本。通过在服务上设置`desired_replicas`来增加。协调器在可能的情况下跨主机和跨可用区传播副本。
```typescript
await miosa.services.update(serviceId, { desiredReplicas: 3 })
```

以循环方式（如果配置了粘性会话则基于哈希）在所有健康副本之间进行流量负载平衡。

## 资源大小

|规格|默认 |每个服务均可调整|
|---|---|---|
|中央处理器| 1 个虚拟CPU |是的 |
|内存| 512 MB |是的 |
|磁盘 | 1 GB 临时 |是的 |
|图形处理器 |无 |不可用（GPU 未产品化） |
|出站带宽 |计量|是的 |

调整大小是按服务、按部署进行的。辅助服务可以比 Web 服务小。

## 日志

运行时实例将 stdout/stderr 流式传输到 MIOSA 的日志平面。日志根据租户的计划保留（默认 7 天）。通过以下方式访问它们：

- `GET /api/v1/deployments/:id/logs`：部署范围内，所有服务
- `GET /api/v1/services/:id/logs`：每项服务
- `GET /api/v1/runtime-instances/:id/logs`：每个实例

日志包括结构化元数据：`service_id`、`runtime_instance_id`、`version_id`、`host_id`。按 `external_workspace_id` 筛选以覆盖白标客户。
