MIOSA 使用交易电子邮件进行平台通知和每个项目
最终用户身份验证流程，例如密码重置和电子邮件确认。

此页面区分了三种不同的电子邮件模式：

|图案|谁拥有它 |示例 |
|---|---|---|
| **MIOSA 管理的身份验证电子邮件** | MIOSA/操作员|密码重置、电子邮件确认、安全通知 |
| **应用程序拥有的交易电子邮件** |生成的应用程序/客户 |收据、预订确认、工作流程通知 |
| **企业/私人发件人设置** | MIOSA + 客户/运营商 |白标签发件人域、私有 SMTP、合规性交付 |

> **注：当前生产型号**
>
> 目前，MIOSA 管理的实时身份验证路径使用重新发送。这并不意味着重新发送
> 客户应用程序可以使用的唯一电子邮件提供商。这意味着内置项目
> 身份验证发送方当前读取平台重新发送配置。

## 电子邮件涵盖哪些内容

|流量|用这个配置？ |笔记|
|---|---:|---|
|项目验证密码重置 |是的 |向生成的应用程序的最终用户发送重置链接。 |
|项目授权电子邮件确认 |是的 |启用电子邮件验证时，注册后发送确认链接。 |
|平台管理员/用户通知 |是的 |使用相同的重新发送 API 密钥以及平台邮件程序设置。 |
|客户申请交易电子邮件 |没有 |将应用程序连接到其自己的提供程序集成或运行时密钥。 |
|客户营销/活动电子邮件 |没有 |通常属于客户应用程序或营销堆栈，而不是 MIOSA 身份验证。 |

## MIOSA 管理的身份验证电子邮件

MIOSA 操作员为内置身份验证即服务产品配置共享交付提供商和发件人身份。
客户应用程序不接收或管理平台交付凭证。

如果平台投递不可用，auth 仍然可以生成重置或确认令牌，但不会投递相应的电子邮件。
不要将成功的密码重置响应视为消息已到达提供商或收件箱的证据。

## 其他提供商选项

对于应用程序级电子邮件，生成的应用程序可以使用
客户选择。常见模式：

|供应商模式|适合 |应该如何接线|
|---|---|---|
| **重新发送** |开发人员友好的交易电子邮件 |将应用程序的 `RESEND_API_KEY` 存储为项目/运行时机密，并从应用程序代码中调用重新发送。 |
| **邮戳** |高送达率交易电子邮件 |将服务器令牌存储为秘密；应用程序拥有模板和发件人验证。 |
| **发送网格** |大型企业电子邮件程序 |将 API 密钥存储为秘密或企业集成；应用程序拥有模板/类别。 |
| **邮枪** |域密集型交易电子邮件 |将 API 密钥/域存储为机密；应用程序拥有路由和日志。 |
| **SMTP 中继** |企业/私人邮件基础设施|将 SMTP 主机/用户/密码存储为机密或配置私有部署路径。 |
| **客户拥有的服务** |受监管或本地环境 |确定企业部署中的网络路径、凭据、审核和数据处理范围。 |

重要规则：应用程序拥有的提供商与 MIOSA 的内置提供商不同
授权邮件程序。应用程序电子邮件属于应用程序运行时； MIOSA 授权电子邮件
属于平台控制平面。

## 平台邮件和通知

平台邮件程序和身份验证即服务使用运营商管理的交付配置。
即使平台通知和应用程序身份验证发送者策略使用相同的提供商，它们也可能有所不同。

不要将成功的密码重置 API 响应视为电子邮件已发送的证据
已发送。检查提供程序配置、日志和提供程序事件仪表板。

## 验证清单

配置环境变量后：

1. 为新项目或沙箱启用项目身份验证。
2. 通过`{AUTH_URL}/signup`创建测试最终用户。
3. 致电 `{AUTH_URL}/password-reset` 获取该电子邮件。
4. 确认后端不记录`email_not_configured`。
5. 确认配置的提供商接受该消息。
6. 确认重置链接到达收件箱并且 `{AUTH_URL}/password-reset/confirm` 接受令牌。

## 白标和企业发件人

如今，内置的身份验证邮件程序是平台操作的。对于白标或
需要来自自己域的邮件的企业客户，请确定这些项目的范围
明确地：- 发件人域和 DNS 记录；
- SPF、DKIM、DMARC、退回邮件和投诉处理；
- MIOSA 是否通过托管提供商或客户的私人 SMTP 发送；
- 每个租户的品牌和模板所有权；
- 审核日志和交付可见性；
- 设置是云、专用网络还是本地。

不要承诺仪表板切换可以让每个项目配置自己的身份验证发送者。

## 应用程序拥有的电子邮件

生成的应用程序仍然可以通过存储提供商凭据来发送自己的电子邮件
作为项目/运行时机密并直接从应用程序代码调用提供程序。
这是收据、邀请、预订等产品电子邮件的正确路径
确认、报告或客户特定的通知。
