智能体不得将单个信号视为生产正常的证据，也不得根据猜测更换持久资源。
此页面涵盖状态解释、持久资源处理和当前功能边界。

## 正确解释状态

> **注意：健康是一个综合结果**
>
> 无法从一个数据库行、一个 HTTP 响应或一个主机检测信号证明部署是健康的。
> 活动版本、运行工件、公共路由、数据绑定、所需功能和运行时放置必须一致。

|信号|它证明了什么 |
|---|---|
|发布状态为 `ready` |不可变产物可以考虑推广 |
|构建状态为 `succeeded` |此版本的构建步骤已完成 |
| `active_release_id` 匹配 |控制平面选择预期发布|
|公共路线回应 |用户可以到达已部署的应用程序表面|
|运行时日志显示启动正常 |进程绑定其端口并正在服务 |

## 保护持久资源

沙箱是一个可变的开发工作区。

部署是持久的生产标识。

托管数据库及其卷是持久的数据资源。

Docker Host 主机可以运行多个部署，并且在没有主机级证据的情况下不应因应用程序级故障而被替换。

在创建替换之前暂停、恢复、恢复和协调现有资源。

仅当原始资源被证明是终端并且其状态、绑定和所有权已被保留时才创建替换。

## 能力边界

MIOSA 目前支持沙箱、计算机、预览、不可变应用程序版本、托管数据、工作区属性、域、集成和 OpenComputers。

现在可以连接专用模型 API。

当 CPU 兼容的开源应用程序的运行时要求适合所选计算时，可以进行自托管。

托管 GPU 执行和内置托管智能体编排仍处于计划中，直到可用性页面将其标记为已发货。

AWS 和 Google Cloud 客户区域包已存在，但生产激活仍然受到提供商金丝雀和主机验收证据的限制。
